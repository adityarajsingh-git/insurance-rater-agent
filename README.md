# Insurance Rater Agent

Upload a motor policy PDF and get the broker commission the insurer's grid gives on it: the Own Damage (OD) and Third Party (TP) rates, the premium each rate applies to, and the expected brokerage in rupees. Every answer cites the policy page it read and the grid cell it used. When the evidence can't settle the answer, the app says so and asks one targeted question instead of guessing.

- **Hosted app:** HOSTED_URL (no sign-in)
- **Decision traces for the four sample policies:** [`traces/`](./traces) (links in the table below)

The HDFC ERGO grid rate depends on the broker's achieved GWP (gross written premium) slab, which isn't printed on any policy. The app shows all five candidate rates with their cells and asks for the slab. Answering it in the UI resolves the rate, for example `>10-50k` gives 17.5%.

The traces are regenerated by `npm run traces`. They come from the committed OCR fixtures, which hold the same page text the hosted app produces in the browser. No answers are applied. A test fails if they go stale.

## How it works

```
browser                                   server (Netlify Function)              storage (Netlify Blobs)
-------                                   -------------------------              -----------------------
pick PDF -> sha256 -> 2.5 MB chunks  --->  POST /api/runs, PUT .../pdf/:i  --->   runs/<id>, chunks/<id>/<i>
pdf.js text layer, else tesseract OCR
(plain + contrast-enhanced pass)     --->  POST /api/runs/:id/pages
                                           analyse(pages)                  --->   run record + every analysis
answer a clarifying question         --->  POST /api/runs/:id/answers  (re-analyses, appends a new revision)
history list / open a run            <---  GET /api/runs, GET /api/runs/:id, GET .../pdf/:i
```

`analyse()` in `src/core/agent.ts` is a pure, deterministic function. It takes page text plus any user answers and returns the facts and the rate:

1. **Identify the insurer.** Each insurer module scores the page text (UIN prefixes, insurer names). The best score above 0.5 wins, and a close runner-up is reported in the trace.
2. **Extract facts with evidence.** `src/core/insurers/<insurer>/extract.ts` reads policy type, business type (new, renewal, rollover), make, model, fuel, CNG kit, cc, seats, registration and RTO, NCB, dates and the premium breakup. Each fact is `found`, `derived`, `missing` or `ambiguous` and carries the page and the quoted line it came from. A second, contrast-enhanced OCR pass fills facts that the de-identification left in faint grey text, such as Go Digit's registration number. The trace records which facts came from that pass.
3. **Resolve against the grid.** `src/core/insurers/<insurer>/resolve.ts` walks the insurer's grid deterministically, in this order: is the grid in force on the policy start date, which sheet applies, how RTO/state maps to the grid's geography, segment, fuel, cc, age, NCB, exclusions, and the footnotes that change the rate. Every step is a trace entry with cell citations (`file`, `sheet`, `cell`, `value`, and why it matters).
4. **Return a result, not just a number.** `resolved` gives a rate with confidence and reason. `ambiguous` gives candidate rates, the fact that decides between them, and a question. `unsupported` gives an evidence-backed refusal, for example a declined combination or a segment the grid doesn't cover. OD and TP are reported separately, and each is `applicable`, `not_applicable` or `unsupported`.

The grids aren't read at request time. `scripts/grids/<insurer>.ts` turns each workbook or rate-card PDF in `raters/` into a normalised JSON table in `src/data/grids/`. One row is one rate cell, with its dimension values and source cell. The scripts assert on the decisive cells, so a changed workbook breaks the build instead of silently changing rates. `npm run grids` regenerates them, and the tests check that the committed JSON is byte-identical.

### Storage and persistence

Uploaded PDFs and completed analyses live in a site-scoped **Netlify Blobs** store named `rater-runs` with strong consistency (`netlify/functions/api.mts`):

- `runs/<id>`: the run record as JSON. It holds file name, size, sha256, upload progress, the page text, the user's answers and **every analysis revision** (the latest is shown, older ones stay selectable). A compact summary sits in the blob's metadata, so the history list costs one `list` call plus metadata reads.
- `chunks/<id>/<index>`: the PDF bytes in 2.5 MB chunks, up to 25 MB per file.

Runs aren't kept in the browser or in function memory. The browser keeps only the open run id in the URL hash. So history and files survive a refresh, closing and reopening the browser, opening the app on another device, function cold starts, and redeploys: site-scoped Blobs aren't tied to a deploy. An interrupted upload can be resumed. Re-select the file, the sha256 must match, and only missing chunks are sent. A run whose text extraction was interrupted can be resumed from the stored chunks without re-selecting the file. There's no sign-in, so the sign-out case doesn't apply, and history is shared by everyone who opens the app.

Local development uses the same API code with a filesystem store under `./.data/` (`FsRunStore`). Tests use an in-memory store and a fake of the Blobs client. One shared test suite runs against all three stores (`tests/server/store.test.ts`).

## Setup, run, test, deploy

Requirements: Node 22+ and npm.

```bash
npm install
npm run dev          # http://localhost:5173, API served by Vite from ./.data (no netlify-cli needed)
npm test             # vitest: grid rebuilds, extraction, resolution, agent pipeline, API, storage, traces
npm run typecheck
npm run build        # static frontend in dist/
npm run traces       # rewrite traces/ for the four sample policies
npm run grids        # rebuild src/data/grids/*.json from raters/
```

**Deploy to Netlify:** `netlify.toml` is already set (`npm run build`, publish `dist`, functions in `netlify/functions`, Node 22). Use either option:

- Netlify UI: *Add new site → Import an existing project →* pick this repo. No environment variables are needed, because Netlify Blobs is configured automatically for the site.
- CLI: `npx netlify-cli login`, then `npx netlify-cli deploy --build --prod`. The first run creates or links the site.

## Architecture notes

- **Deterministic engine, no LLM at runtime.** Commission lookup is a rules problem with a provable answer, so the engine is plain TypeScript: reproducible, unit-tested, and every number traceable to a cell. An LLM could help with extraction on unseen layouts, but here it would make the answer non-reproducible and harder to audit.
- **One module per insurer behind one interface** (`src/core/insurers/module.ts`): `detect`, `extract`, `resolve`. Each grid's geography (states, zones, clusters, RTO lists), segment model and footnotes are different enough that one generic resolver would hide the traps. Shared parsing such as money, dates, registration marks and the RTO-to-state map lives in `src/core/extract/common.ts` and `src/core/geo.ts`.
- **Text extraction happens in the browser.** pdf.js reads the text layer when a page has one. Otherwise the page is rendered at 300 dpi and OCR'd with tesseract.js, which applies to all four samples because they're scans. This keeps the function small and fast, and lets the user watch per-page progress. The server stores the page text, so re-analysis never re-runs OCR.
- **The API is framework-free.** `src/server/api.ts` is one `handleApi(Request) → Response` function. The same code runs in the Netlify Function, the Vite dev server and the tests.

## Assumptions (each one is also stated in the relevant trace)

- **Grid in force.** Grids without an end date apply from their start date. Go Digit's Mar'26 workbook is taken to cover 1-31 Mar 2026. A policy that starts outside a grid's window still gets a rate, with a warning step. The Reliance sample starts 23 Dec 2025, but only the Feb'26 grid was supplied.
- **Business type.** A policy that names the same previous insurer is a renewal, a different previous insurer is a rollover, and no previous policy is new business. This is derived when no tick box survives OCR.
- **Fuel.** When fuel isn't printed, it's derived only when the model has a single fuel variant (Reliance: Renault KWID, petrol). Otherwise it becomes a question. A CNG/LPG kit is read from the kit IDV or kit TP line.
- **Premium base.** Each grid names its base: basic TP, net OD, net premium, and so on. The base is taken from the policy's premium table, before GST. HDFC ERGO prints one Package rate with no OD/TP split, so it's applied to both. That's an interpretation, so confidence is lowered to medium.
- **Reliance small-car adjustment** (`PC!H3`, "payout for < 1000 cc will be 5% lesser"). It's read as 5 percentage points off the grid rate, so the 999 cc sample gets 22.5 - 5 = 17.5%. The alternative reading (×0.95 = 21.375%) is recorded in the trace.

## Failure modes and how they surface

| Situation | Behaviour |
|---|---|
| Insurer not in `raters/`, or not recognised | `unsupported`, with the detection scores in the trace and a question asking which supported insurer issued the policy. There's no guessing from a different insurer's grid. |
| Fact missing or unreadable (OCR) | `ambiguous`, with the candidate rates and a question for that fact. The user's answer is stored as `user` evidence and re-analysed. |
| Declined or excluded combination, or a segment the grid doesn't have | `unsupported` or `not_applicable`, citing the declining cell or footnote |
| Policy outside the grid's dates | rate given, with a `warn` step |
| Low OCR confidence on a page | `warn` step naming the pages. Facts keep their quotes, so they can be checked against the PDF. |
| Upload interrupted or browser closed mid-run | run stays `uploading` or `awaiting_text` in history and can be resumed |
| Engine error | run saved as `failed` with the error, and retrying the analysis needs no re-upload |
| Offline browser | tesseract.js loads its worker and English data from the jsDelivr CDN, so scanned PDFs need internet access |

## Trade-offs and next steps

- **No authentication.** It keeps the reviewer flow one click and history is global. Real use needs sign-in and per-user scoping. The store is already behind one interface, so the change is local.
- **Per-insurer extractors are layout-aware.** New layouts from a supported insurer usually work, because they match on labels, not positions. A completely new format can still miss facts, and those then show as questions rather than wrong answers.
- **OCR in the browser** saves server cost but depends on the client device's speed: roughly 2-5 s per page on a laptop.
- **Grids are compiled at build time.** A new month's grid means adding the file to `raters/`, running `npm run grids` and redeploying. An upload-a-grid flow would be the next feature.
